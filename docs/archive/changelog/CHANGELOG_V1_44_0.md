# 1.44.0 (versionCode 108) — Stalker VOD: `create_link` παρακαμπτόταν

Η αιτία. Δεν ήταν ούτε μηχανή, ούτε codec, ούτε πρωτόκολλο, ούτε token που λήγει.

---

## Το σφάλμα

`StalkerClient.resolve()` ξεκινούσε με μια συντόμευση:

```kotlin
// 1) το cmd συχνά περιέχει ήδη το URL
val direct = Regex("https?://\\S+").find(cmd)?.value ?: ""
if (direct.isNotEmpty() && ...) {
    return direct          // ← ΠΑΡΑΚΑΜΠΤΕΙ ΤΟ create_link
}
```

**Για ζωντανά είναι σωστό.** Το `cmd` του `itv` είναι συχνά ο τελικός σύνδεσμος, και
η συντόμευση γλιτώνει ένα round-trip σε κάθε αλλαγή καναλιού — η πιο συχνή ενέργεια
σε IPTV.

**Για ταινίες και επεισόδια είναι λάθος.** Εκεί το `cmd` περιέχει σύνδεσμο με token
που παρήχθη τη στιγμή που κατέβηκε ο **κατάλογος**. Ο σύνδεσμος ενεργοποιείται μόνο
όταν περάσει από `create_link`.

Χωρίς αυτό, ο πάροχος απαντά **HTTP 404** — δεν λέει «απαγορεύεται», λέει «δεν
υπάρχει». Γι' αυτό έμοιαζε με χαλασμένο αρχείο αντί για ανενεργό σύνδεσμο, και γι'
αυτό κυνήγησα επτά εκδόσεις τη λάθος μεριά.

## Γιατί ταίριαζε με ΚΑΘΕ συμπτωμα

| παρατήρηση | εξήγηση |
|---|---|
| τα ζωντανά παίζουν | η συντόμευση είναι σωστή για `itv` |
| οι ταινίες όχι, **στην ίδια πηγή** | παρακάμπτεται το `create_link` |
| το ίδιο και στις σειρές | ίδιος δρόμος (`series_ep`) |
| **ανανέωση δεν βοήθησε** | νέος κατάλογος → νέο `cmd`, αλλά πάλι χωρίς `create_link` |
| παίζει στο Ultimate | εκείνο καλεί πάντα `create_link` |
| 404 και όχι 403 | ανενεργό token, όχι απαγόρευση |

Κάθε μία από αυτές τις παρατηρήσεις μου την είχες δώσει. Το μοτίβο ήταν εκεί από
την αρχή· εγώ κοίταζα τη μηχανή αναπαραγωγής.

## Η διόρθωση

```kotlin
fun resolve(cmd: String, vod: Boolean = false): String
```

- **ζωντανά** (`vod = false`): συντόμευση όπως πριν
- **ταινίες/επεισόδια** (`vod = true`): **πάντα** `create_link`, ποτέ συντόμευση

Μπήκε και δεύτερη βελτίωση: για VOD δοκιμάζεται **πρώτα** ο τύπος `vod` και μετά
`itv`. Πριν ήταν πάντα `itv → vod`, που για κάθε ταινία σπαταλούσε ένα round-trip —
και σε κάποιους portal ο λάθος τύπος επιστρέφει σκουπίδια αντί για κενό.

Το `direct` παραμένει ως **έσχατη λύση**: αν το `create_link` δεν δώσει τίποτα,
καλύτερα να δοκιμάσει ο player και να αποτύχει, παρά να μη δοκιμάσει καθόλου.

### Δύο σημεία κλήσης, όχι ένα

- `Repository.playableUrl` → ο player
- `RelayHub.resolve` → το relay (μετάδοση σε άλλη συσκευή)

**Και τα δύο** διορθώθηκαν. Αν διόρθωνα μόνο το πρώτο, το relay θα σέρβιρε τους
ίδιους νεκρούς συνδέσμους — το κλασικό λάθος αυτού του project, που κυνηγάμε όλη
τη συνεδρία.

## Τι κρατάει από τη δουλειά 1.43.x

Η αιτία ήταν αλλού, αλλά τίποτα δεν πάει χαμένο:

- **RTSP / RTMP / UDP / MMS / γυμνό `.ts`** παίζουν τώρα και δεν έπαιζαν ποτέ
- **εφεδρεία σε LibVLC** όταν το ExoPlayer αποτύχει ή δεν ξεκινήσει σε 7″
- **ίδιος User-Agent** και στις δύο μηχανές
- **ξεχωριστά μηνύματα σφάλματος** — χωρίς αυτά, δεν θα ήξερα ποτέ ότι το
  `engine.open()` καλούνταν κανονικά και το 404 ερχόταν από τον διακομιστή

Το LibVLC ήταν αυτό που έφερε το `HTTP 404` στο logcat. Το ExoPlayer σιωπούσε.
