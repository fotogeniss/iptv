# 1.42.1 (versionCode 98)

Δύο διορθώσεις από την ανασκόπηση του billing, και μία εκκρεμότητα που έκλεισε.

---

## Α. Η εισαγωγή είχε δύο απαντήσεις στην ίδια ερώτηση

`SplashProgressPolicy.canDismiss()` έλεγε ρητά στο σχόλιό του **«δεν υπάρχει
μέγιστος χρόνος»**, ενώ το `PreludeSplash` είχε δεύτερο `LaunchedEffect` με
χρονόμετρο 8 δευτερολέπτων που το policy δεν γνώριζε.

Χειρότερα: το `canDismiss` **δεν καλούνταν από πουθενά**. Ζούσε μόνο μέσα στα
tests του — τέσσερα tests που φύλαγαν συμπεριφορά την οποία η εφαρμογή δεν είχε.
Ένα από αυτά, το `δεν υπάρχει μέγιστος χρόνος`, περνούσε και ήταν **λάθος**.

### Τι μπήκε στη θέση του

```kotlin
fun remainingMs(finished: Boolean, visibleMs: Long): Long
```

Επιστρέφει **αναμονή**, όχι ναι/όχι. Ο λόγος:

> Με ένα `canDismiss` η οθόνη πρέπει να το ρωτά συνέχεια — δηλαδή να μετρά χρόνο
> μόνη της. Και μόλις μετρήσει χρόνο μόνη της, αποκτά δικούς της κανόνες, που αργά
> ή γρήγορα διαφωνούν με τους εδώ.

Το `PreludeSplash` έχει τώρα **ένα** effect που ρωτά, περιμένει όσο του πουν, και
ξαναρωτά. Δεν αποφασίζει τίποτα.

Το `delay(320)` («να προλάβει η μπάρα να φτάσει στο τέρμα») ήταν σταθερά κρυμμένη
μέσα σε effect· έγινε `SETTLE_MS` μέσα στο policy, όπου φαίνεται μαζί με τους
υπόλοιπους κανόνες.

**Νέα tests** (6, στη θέση των 4): το πάνω όριο διώχνει την εισαγωγή ακόμη κι αν
φορτώνει, το πάνω όριο **υπερισχύει** του κάτω, και μια σάρωση που επιβεβαιώνει ότι
`visible + remaining` δεν ξεπερνά ποτέ το πάνω όριο.

## Β. Νεκρό κουμπί για τους δωρεάν χρήστες

```kotlin
onEditHome = { editing = true }
...
if (editing && canEditHome) { … }
```

Ο δωρεάν χρήστης πατούσε «Επεξεργασία αρχικής» και **δεν συνέβαινε τίποτα**. Ούτε
οθόνη, ούτε μήνυμα, ούτε προσφορά.

Είναι το χειρότερο δυνατό αποτέλεσμα: ο χρήστης νομίζει ότι η εφαρμογή είναι
χαλασμένη — τη στιγμή ακριβώς που δήλωνε ότι θέλει τη δυνατότητα. Ένα κλείδωμα που
δεν εξηγείται δεν πουλά· εκνευρίζει.

### Νέο `billing/PremiumRequiredDialog.kt`

Ένας διάλογος για **και τις επτά** `PremiumFeature`, όχι ένας ανά οθόνη. Επτά
διάλογοι θα σήμαιναν επτά κείμενα, επτά φορές ξεχασμένη η «Επαναφορά αγοράς», και
επτά σημεία να διορθωθούν όταν αλλάξει η τιμή.

Τρεις αποφάσεις μέσα του:

- **Η τιμή έρχεται από το Play** (`state.offer.formattedPrice`), όχι γραμμένη από
  εμάς — αλλιώς δείχνει λάθος νόμισμα σε κάθε χώρα εκτός της δικής μας.
- **Το κουμπί αγοράς είναι ανενεργό χωρίς πραγματική προσφορά.** Ένα κουμπί που
  δεν μπορεί να αγοράσει είναι το ίδιο πρόβλημα σε άλλη θέση.
- **Η «Επαναφορά αγοράς» φαίνεται πάντα**, ακόμη και χωρίς σύνδεση με το Play. Ο
  χρήστης που άλλαξε συσκευή **έχει ήδη πληρώσει**· το να ξαναπληρώσει επειδή δεν
  βρήκε το κουμπί είναι ό,τι χειρότερο μπορεί να του συμβεί.

Η απόφαση παίρνεται πλέον **τη στιγμή του πατήματος**:

```kotlin
onEditHome = {
    if (canEditHome) editing = true
    else lockedFeature = PremiumFeature.EDIT_HOME
}
```

Ή ανοίγει η οθόνη, ή εξηγείται γιατί όχι. Καμία σιωπηλή συνθήκη παρακάτω.

## Γ. Το `hasQaPremiumOverride()` δεν το καλούσε κανείς

Τώρα η κεφαλίδα γράφει **«PREMIUM · QA»** όταν το premium προέρχεται από το
`BuildConfig` και όχι από αγορά.

Χωρίς αυτό, δοκιμάζοντας δεν ξεχωρίζεις αν κάτι δουλεύει επειδή το πλήρωσες ή
επειδή η σημαία το ανοίγει — και τότε τα κλειδώματα δεν δοκιμάζονται ποτέ στα
σοβαρά.

## Εκκρεμεί ακόμη

Η επαλήθευση αγοράς γίνεται **στη συσκευή** (`DevicePurchaseVerifier`). Σε rooted
συσκευή ή patched APK παρακάμπτεται. Το `PurchaseVerifier` είναι ήδη interface, και
το `VerificationLevel.SERVER` υπάρχει — η υποδομή περιμένει backend. Απόφαση, όχι
παράλειψη.
